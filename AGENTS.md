# Project requirements

## REQUIRED: Xcode Code Intelligence build and test workflow

- **When the user says this agent is running through Xcode Code Intelligence, or the invocation context identifies Xcode Code Intelligence, you MUST use Xcode's built-in build and test tools first.** This is a required tool-selection rule, not an optional preference.
- Discover the available Xcode tools before choosing a build or test command. Do not assume they are unavailable merely because they are not listed in the initial tool summary.
- **Do not run shell-based builds/tests, repository build/test scripts, or direct `xcodebuild` commands when Xcode's built-in tools can perform the required validation.** A familiar or preconfigured command is not a reason to bypass this rule.
- **Do not request additional sandbox permissions for a shell build/test that can be performed with Xcode's built-in tools.** Use the built-in tools instead.
- Fall back to command-line validation only after establishing that the relevant Xcode tool is unavailable or cannot perform the required validation. State the specific limitation before using the fallback; do not silently switch to shell commands.
- All signing, bundle identifier, Derived Data, and validation restrictions below still apply. Run hosted unit tests only: select `TunesTests` and exclude `TunesUITests`. Built-in Xcode tools do not authorize UI tests, app launches for visual validation, or screenshots.

## General requirements

- Keep all repository documentation, source comments, test descriptions, and app-owned text in English. User-provided project, track, and file names retain their original text.

- Provide manual verification instructions in chat only; do not maintain manual verification checklists in repository documentation.
- Never use Computer Use, browser automation, accessibility control, or UI test runners to validate this project. Use builds and unit/protocol tests; provide instructions for the user to verify the UI and live Samply flows manually.
- Never launch the app and capture screenshots to validate its UI, whether through Xcode, shell commands, screenshot tools, or any other method. Do not use screenshots or visual inspection of a running app as a substitute for Computer Use. UI verification must be performed manually by the user; hosted unit tests remain allowed without visual inspection or screenshots.
- Signing policy: local development with the owner's free Personal Team. Keep automatic `Apple Development` signing and existing team `YM5G2M8PV9` for Debug, Release, and test targets. No Developer ID distribution or notarization is configured. Never override signing with ad hoc (`CODE_SIGN_IDENTITY=-`), disable signing (`CODE_SIGNING_ALLOWED=NO`), or switch teams/certificates as a fallback. If credentials are missing, expired, or inaccessible, report the prerequisite failure; do not automatically provision, create, revoke, import, or export certificates or modify Apple account credentials. Xcode/codesign may use the existing signing identity normally; this does not permit Tunes application code to access Keychain. Use temporary Derived Data for builds/tests, do not replace installed apps, and run hosted unit tests only (`-only-testing:TunesTests -skip-testing:TunesUITests`). See README.md for the signing policy.
- Debug app bundle identifier is `com.lloydME.Tunes.beta`. Release is `com.lloydME.Tunes`. Keep Debug/Release web sessions isolated. Check identifiers before building or launching.
- Tunes must not read, write, delete, migrate, or inspect the local Keychain. Development tools such as Git may use their existing credential helpers, including Keychain. The user explicitly selected local plaintext file storage for personal access tokens. Keep the file in the app container with directory permissions 0700 and file permissions 0600, exclude it from backups, and isolate Debug/Release storage. Restore only for the matching Samply web account; delete the file on sign-out, account change, or explicit token removal. Do not put PATs in preferences, logs, or JavaScript.
- Browser sign-in must use official Samply authorization only. The user explicitly requested pasting Samply's official email sign-in link into the app; open it unchanged in the app's existing WebKit session so email-provider redirects and Samply complete authentication. Do not validate the sign-in link's domain, path, action parameters, or email-provider wrapper format. Never log or persist the pasted link in app settings. No extensions, bookmarklets, user scripts, exported session tickets, browser profile access, cookie exports, refresh-token imports, or undocumented authentication SDK calls. Do not touch Apple credentials or identity. Never substitute an Apple-styled button for native authorization.
- Do not expose a browser authorization entry point until Tunes has an official registered client and a supported route to the full Library/player session. API OAuth alone does not establish the web player's session. See Docs/AuthenticationDesign.md.
- All app-owned UI, menus, accessibility labels, status messages, and errors must be in English. User-provided project, track, and file names keep their original text.
- Prefer native SwiftUI/AppKit UI. Samply's web engine currently owns authenticated streaming. Keep undocumented playback/library integration isolated behind the versioned JavaScript adapter.
- Never use download URLs as a fallback for streaming or change Samply's access/download/version permissions.
- Scope: browse/play Library, folders and versions, playback controls, media keys, and optional original-file upload. Comments/collaboration editing are out of scope.
